## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/blip_vqa_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 8-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False` through `BlipForQuestionAnswering`/`BlipProcessor`. The upstream `pytorch_model.bin` and `tf_model.h5` are not listed and not used; the notebook's only external dependencies are the pinned PyPI distributions and the Hub at the model revision.
- **Role stages:** `validate_inputs` writes `outputs/blip_vqa_input_manifest.json` with the schema (384×384 resize, decoding rule), the ceilings, the input's observed mode and size, the checked questions, the budget, the verdict, and one recorded rejection finding from the blank-question probe; `evaluation_report` writes `outputs/blip_vqa_evaluation_report.json` — `sample-sanity` with the `exact_match` rate, the mean `anls` and one entry per question on the synthetic scene; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 640×480 cartoon scene drawn in code with Pillow (no text rendering, so its digest is stable across Pillow builds) — the same drawing the smoke run used; `exact_match`/`anls` against facts you drew yourself are sanity evidence for the input contract, forward pass and decoding, not a VQA metric. **Two of the seven questions are recorded misses** (the smoke run counted `2` trees where one is drawn and called the brown door `red`); they stay in the scored set so the report shows what a wrong answer looks like.
- Score semantics (UNC1–UNC4): the answer is generated text with no score, probability or correctness signal; the notebook says so before the first answer and again in the interpretation section, and states that the model answers unanswerable questions (blank image → `dog` in the smoke run). The token budget is a caller-owned request parameter exposed as a `# @param` value (default `DEFAULT_MAX_NEW_TOKENS = 10`) and passed explicitly on every `answer` call; `truncated` is surfaced and explained. The notebook performs no validation of its own — image, questions and budget are checked only by the pipeline's `validate_inputs`/`answer` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `IMAGE_SIZE` (384), `MAX_QUESTION_CHARS` (256), `MAX_NEW_TOKENS` (32), `DEFAULT_MAX_NEW_TOKENS` (10) and `DECODING` are printed before the model runs.
- CPU is documented as adequate (card-measured 5.6–5.8 s load, about 0.2 s per question on the 640×480 scene; 0.66 s on a 4096×4096 blank image); the notebook states that cost is per question and that GPU output need not match CPU output token-for-token.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
